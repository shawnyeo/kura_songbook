# 쿠라맛챠 노래책 룰북 v0.94

## 0. 문서 목적

이 문서는 쿠라맛챠 노래책의 **DB 입력 규칙, taxonomy 규칙, 공개 UI 원칙, 장기 확장 방향**을 정리한 프로젝트 룰북이다.

이 문서는 세부 수식 명세서가 아니다. 셀 위치, QUERY 수식, helper 시트 구조는 별도 문서인 `kura_songbook_sheet_architecture_spec.md`를 따른다.

---

## 1. 프로젝트 목적

쿠라맛챠 노래책은 스트리머와 시청자가 방송 중 빠르게 곡을 찾고 고르기 위한 **Google Sheets 기반 노래 검색/선택 UI + 관리용 DB**다.

이 노래책은 단순한 곡 설명 DB가 아니다.

핵심 목표는 다음과 같다.

| 목표 | 설명 |
|---|---|
| 빠른 검색 | 제목, 번역명, 가수, 언어, 장르, 주제, 출처로 빠르게 찾기 |
| 곡 선택 보조 | 곡의 분위기, 상황, 출처를 짧게 보여줘 선택을 돕기 |
| 방송 사용성 | 스트리머와 시청자가 방송 중 바로 활용 가능해야 함 |
| 관리 확장성 | 검색 UI, 랜덤 추천, 부른 횟수, 가사 링크, 로그 기능으로 확장 가능해야 함 |
| 입력 편의성 | 새 곡을 빠르게 추가하고 표준화할 수 있어야 함 |
| 공개 가독성 | 시청자용 화면은 짧고 직관적이어야 함 |

한 줄 정의:

> 짧은 구조화 정보로 곡을 바로 고르게 만드는 방송용 노래 검색 UI.

## 2. 기본 설계 철학

## 2.1 DB와 사용자 UI를 분리한다

한 시트가 원본 DB, 검색 엔진, 공개 화면, 작업용 입력을 모두 맡으면 금방 복잡해진다.

따라서 다음 레이어를 구분한다.

| 레이어 | 역할 |
|---|---|
| `DB_RAW` | 원본 데이터. 컬럼이 많아도 됨 |
| `검색_ENGINE` | QUERY 기반 검색 결과를 만드는 내부 엔진 |
| `QUERY_BUILDER` | 검색 조건 조각을 만드는 helper |
| `CARD_HELPER` | 검색 결과를 사용자 카드형 표시값으로 변환 |
| `검색_UI_PC` | 데스크탑용 공개 검색 화면 |
| `검색_UI_MOBILE` | 모바일 세로형 공개 검색 화면 |
| `TAXONOMY` | 장르/주제/출처 표준어 관리 |
| `가사_INDEX` | 가사/발음/해석 링크 허브 |
| `작업용` | 복붙/임시 입력/검수 전 데이터 |
| `BACKUP` | 작동본 백업 |

핵심 원칙:

> DB는 넓고 정확하게. 검색 엔진은 숨기고 안정적으로. 사용자 UI는 짧고 예쁘고 빠르게.

---

## 2.2 사용자 화면은 DB 표가 아니라 검색 결과 페이지처럼 만든다

관리자용 DB는 넓은 표여도 된다. 하지만 시청자가 보는 화면은 20개 컬럼짜리 원본 DB가 아니라, 곡 선택에 필요한 핵심 정보만 보여줘야 한다.

사용자 화면에서 우선 표시할 정보:

| 정보 | 이유 |
|---|---|
| 제목 | 곡 식별의 기준 |
| 번역명 | 한국어 사용자 이해 보조 |
| 가수 | 곡 구분 |
| 언어 | 선택 기준 |
| 장르 | 곡 분위기 판단 |
| 주제/설명 | 상황·대상·감정 파악 |
| 비고/출처 | OST, 인디, 바이럴 등 맥락 제공 |
| 링크 | 영상 확인 |
| 부른 횟수 | 필요시 운영/추천 보조 |

관리자용 또는 숨김 정보:

| 정보 | 처리 |
|---|---|
| 장르1/장르2/장르3 | 검색용 원자 컬럼 |
| 상황/대상/감정 | 검색용 원자 컬럼 |
| 출처유형/매체/작품명/기타태그 | DB 관리용 메타 |
| 링크URL 원문 | 표시용 링크와 분리 |
| 발매년도 | 기본 숨김 가능 |
| 상태 | 관리자용 |

## 3. 공개 사용 방식

## 3.1 공개 방식은 두 단계로 나눈다

### 1단계: 정적 VIEW

가장 안정적인 공개 방식이다.

| 방식 | 설명 |
|---|---|
| Ctrl+F | 제목, 번역명, 가수, 한국명, 작품명 검색 |
| 헤더 필터 | 언어, 장르, 비고, 부른 횟수 등 필터 |
| 필터뷰 링크 | 일본어곡, 애니곡, 발라드곡 등 바로가기 |
| 보호된 원본 DB | DB_RAW는 편집 방지 |

### 2단계: 검색 UI VIEW

v1.0 목표다.

| 기능 | 설명 |
|---|---|
| 자유검색창 | 제목, 가수, OST, 틱톡, 요네즈 등 검색 |
| 드롭다운 필터 | 언어, 장르, 상황, 대상, 감정, 출처 등 |
| 카드형 결과 | 표보다 보기 쉬운 검색 결과 |
| 랜덤 추천 | 현재 결과 랜덤, 전체 랜덤 |
| PC/모바일 분리 | 반응형 대신 별도 시트 |

주의:

- Viewer 권한만으로는 셀 입력형 검색창을 사용할 수 없다.
- 검색 UI를 공개하려면 제한적 편집 권한, 보호 범위, 백업 시트가 필요할 수 있다.
- 전체 공개 편집은 충돌 위험이 있으므로 보호 범위와 복구 계획을 함께 둔다.

## 4.2 표시용 컬럼과 검색용 컬럼을 구분한다

| 표시용 | 검색/관리용 |
|---|---|
| 장르 | 장르1, 장르2, 장르3 |
| 설명 또는 주제표시 | 상황, 대상, 감정 |
| 비고 | 매체, 출처유형, 작품명, 기타태그 |
| 링크표시 | 링크URL |

원칙:

- 사용자에게는 표시용 컬럼을 우선 보여준다.
- 검색 엔진은 가능한 한 원자 컬럼을 사용한다.
- 표시용 컬럼은 가독성을 위해 합친다.
- 원자 컬럼은 DB 확장과 정확한 필터링을 위해 유지한다.

## 4.4 제목

원문 제목을 유지한다.

| 언어 | 예시 |
|---|---|
| 일본어 | 夜明けと蛍 |
| 중국어 | 起风了 |
| 한국어 | 바람꽃 |
| 영어 | Lemon Tree |

규칙:

- 원제 우선.
- 일본어/중국어는 원문 유지.
- 한국어 곡은 공식 한국어 제목 사용.
- 괄호가 공식 제목에 포함된 경우 유지.
- 검색 편의를 위해 제목을 임의 번역하지 않는다.

---

## 4.5 번역명

한국어 사용자가 곡 의미를 빠르게 파악하기 위한 칸이다.

규칙:

- 자연스러운 한국어 번역.
- 직역보다 곡 제목처럼 읽히는 번역 우선.
- 공식 한국어 제목이 있으면 공식명 우선.
- 번역이 애매하거나 고유명사면 공백 허용.
- 한국어 원곡이면 공백 가능.

예시:

| 제목 | 번역명 |
|---|---|
| 夜明けと蛍 | 새벽과 반딧불이 |
| 君に最後の口づけを | 너에게 마지막 입맞춤을 |
| なんでもないや | 아무것도 아니야 |
| 起风了 | 바람이 불어 |

## 4.6 가수

원어 또는 공식 표기를 유지한다.

규칙:

- 일본어 가수는 일본어/공식 로마자 표기 우선.
- 한국어 가수는 한국어 표기.
- 영어권 가수는 영어 표기.
- 커버곡은 원곡자 기준인지 커버자 기준인지 비고 또는 기타태그에 명시 가능.
- 스트리머가 부르는 특정 커버 버전이 중요하면 가수는 커버자, 기타태그에 `커버` 입력 가능.

예시:

| 가수 |
|---|
| n-buna |
| 米津玄師 |
| LiSA |
| たかやん |
| 아이유 |

---

## 4.7 한국명

가수명의 한국어 발음 기반 표기다.

규칙:

- 가능하면 채운다.
- 너무 유명한 로마자명은 생략 가능.
- 가수명이 이미 한국어면 공백 가능.
- 보컬로이드/프로젝트명은 통용 표기 우선.

예시:

| 가수 | 한국명 |
|---|---|
| 米津玄師 | 요네즈 켄시 |
| たかやん | 타카얀 |
| n-buna | 나부나 |
| LiSA | 리사 |
| HoneyWorks | 허니웍스 |

# 5. 장르 taxonomy

## 5.1 장르 기본 원칙

장르는 음악 시장 구분이 아니라 **청감/스타일 기준**이다.

규칙:

- 기본 1~2개.
- 특수한 경우 3개까지 허용.
- `J-pop`, `K-pop`, `C-pop`은 장르로 쓰지 않는다.
- 새 장르 추가 가능.
- 단, 비슷한 단어를 중복 생성하지 않는다.
- 표기는 TAXONOMY 시트의 표준어를 따른다.

# 6. 주제 taxonomy

## 6.1 기본 원칙

기존의 `주제` 1칸은 사람이 보기에는 좋지만, DB 관리에는 불리하다.
따라서 DB 내부에서는 다음 3컬럼으로 나눈다.

| 컬럼 | 의미 |
|---|---|
| 상황 | 곡의 큰 장면/맥락 |
| 대상 | 관계, 대상, 테마 축 |
| 감정 | 감정, 상태, 에너지 |

공개 화면에서는 이 3개를 합쳐서 `주제표시` 또는 `설명`으로 보여준다.

형식:

```text
상황 / 대상 / 감정
```

예시:

| 상황 | 대상 | 감정 | 표시 |
|---|---|---|---|
| 사랑 | 짝사랑 | 설렘 | 사랑 / 짝사랑 / 설렘 |
| 이별 | 거리 | 그리움 | 이별 / 거리 / 그리움 |
| 성장 | 전투 | 결의 | 성장 / 전투 / 결의 |
| 밈 | 도발 | 광기 | 밈 / 도발 / 광기 |

## 6.5 주제 입력 규칙

- `상황`, `대상`, `감정`을 각각 1개씩 입력한다.
- 공개 표시값은 `상황 / 대상 / 감정` 형태로 만든다.
- 문장형 설명 금지.
- 하나의 칸에 여러 감정을 억지로 넣지 않는다.
- 기존 pool에 없으면 추가 가능하되, 비슷한 단어가 있는지 먼저 확인한다.
- 너무 추상적인 단어는 피한다.

나쁜 예:

| 나쁜 값 | 이유 |
|---|---|
| 좋은 노래 | 판단이지 주제가 아님 |
| 감성적 | 너무 넓음 |
| 관계 | 너무 일반적 |
| 슬픈 사랑 이야기 | 문장형 |
| 사랑/슬픔/이별/추억 | 원자값 아님 |

좋은 예:

| 상황 | 대상 | 감정 |
|---|---|---|
| 사랑 | 짝사랑 | 설렘 |
| 이별 | 기억 | 후회 |
| 팬덤 | 최애 | 질투 |
| 전투 | 운명 | 결의 |
| 밈 | 도발 | 광기 |

## 6.6 UI용 taxonomy 압축 원칙

| 구분 | 역할 |

| UI shortcut taxonomy | 사용자 필터용 압축 목록 |

| 분위기 |

- 자유검색이 있으므로 모든 taxonomy를 드롭다운에 노출할 필요는 없다.

# 8. 링크 규칙

## 8.1 기본 원칙

링크는 완벽한 버튼 UI보다 **raw URL 보존**을 우선한다.

Google Sheets에서 링크 버튼화가 일관되지 않을 수 있으므로, 링크 문제 때문에 전체 노래책 진행을 막지 않는다.

---

## 8.2 링크URL

규칙:

- 가능하면 유튜브 공식 영상.
- 공식 영상이 없으면 대표 영상.
- 커버곡이면 해당 커버 버전 링크.
- URL을 raw text로 보존.
- 링크가 없으면 공백 허용.
- URL이 아니라 영상 제목/검색어만 있는 경우 `검수필요` 또는 `링크필요` 태그를 붙일 수 있다.

---

## 8.3 링크표시

공개 화면에서는 다음 중 하나로 표시한다.

| 표시 | 의미 |
|---|---|
| ▶ 영상 | URL 있음 |
| YouTube | 유튜브 링크 있음 |
| 검색 | 직접 검색 권장 |
| 공백 | 링크 미정 |

주의:

- `HYPERLINK`는 실제 URL일 때만 안정적으로 쓴다.
- 링크URL이 URL이 아니면 `HYPERLINK`가 깨질 수 있다.

# 10. 부른 횟수 규칙

`부른 횟수`는 공식 운영 컬럼이다.

목적:

| 목적 | 설명 |
|---|---|
| 방송 로그 | 몇 번 불렀는지 추적 |
| 곡 추천 | 많이/적게 부른 곡 구분 |
| 팬 요청 관리 | 자주 부른 곡과 안 부른 곡 확인 |
| 레퍼토리 분석 | 스트리머의 실제 선호 파악 |
| 랜덤 추천 | 안 부른 곡/적게 부른 곡 우선 추천 가능 |

규칙:

- 숫자만 입력.
- 모르면 공백 또는 0.
- 부른 기록이 확인되면 증가.
- 가능하면 나중에 `LOG` 탭과 연결.
- 공개 VIEW에는 표시 가능.
- 단, 시청자가 부담스럽게 느끼면 숨김 가능.

# 15. TAXONOMY 관리 규칙

TAXONOMY는 실제 DB_RAW에 들어간 값과 싱크되어야 한다.

원칙:

- DB_RAW에 있는 값은 TAXONOMY에도 있어야 한다.
- TAXONOMY에만 있고 DB_RAW에 없는 값은 허용하되, 너무 많으면 UI가 복잡해진다.
- 사용자 드롭다운이 길어지면 UI shortcut taxonomy를 만든다.
- 상세 taxonomy는 관리용으로 유지한다.

검수 포인트:

| 확인 | 예시 |
|---|---|
| DB 값이 taxonomy에 있는가 | 대상=`재회`가 TAXONOMY 대상에 있어야 함 |
| 표기 통일 | `록` vs `락` |
| 중복 의미 | `애틋함`과 `아련함` 과다 중복 여부 |
| UI 압박 | 드롭다운이 너무 길지 않은가 |

---

# 16. 가사_INDEX 방향

가사 기능은 사용성 측면에서 중요하다.
다만 전체 가사를 시트에 직접 저장하지 않는다.

`가사_INDEX`는 링크 허브로 만든다.

권장 컬럼:

| 컬럼 | 설명 |
|---|---|
| song_id | DB_RAW와 연결 |
| 제목 | 곡명 |
| 가사링크 | 원문 가사 |
| 발음링크 | 한글 발음/독음 참고 |
| 해석링크 | 한국어 해석 참고 |
| 노래방/MR | MR/노래방 영상 |
| 발음주의 | 어려운 발음 메모 |
| 시작가사 | 첫 소절 정도 |
| 주의사항 | 방송용 주의사항 |
| 상태 | 완료/검수필요/링크필요 |

원칙:

- 전체 가사 저장보다 링크 허브 우선.
- 외국어 곡은 원문 + 발음 + 한국어 의미가 같이 있는 자료를 우선.
- 자주 부를 곡부터 5~10개씩 채운다.

# 17. 데이터 입력 우선순위

새 곡을 추가할 때 우선순위는 다음과 같다.

| 우선순위 | 항목 |
|---:|---|
| 1 | 제목 |
| 2 | 가수 |
| 3 | 언어 |
| 4 | 장르1 |
| 5 | 상황/대상/감정 |
| 6 | 비고표시 또는 출처유형 |
| 7 | 번역명 |
| 8 | 한국명 |
| 9 | 링크URL |
| 10 | 발매년도 |
| 11 | 부른 횟수 |

모든 정보를 한 번에 완벽하게 채우려고 하지 않는다.
노래책 진행을 막는 정보는 나중에 검수한다.

# 19. 소스 파일 운영 규칙

이 룰북 외에 별도 소스 파일을 둔다.

| 소스 파일 | 역할 |
|---|---|
| `노래_룰북.md` | DB 입력, taxonomy, 운영 원칙 |
| `kura_songbook_sheet_architecture_spec.md` | 시트명, 셀 위치, 컬럼 매핑, QUERY 수식 |
| `kura_songbook_ui_implementation_plan.md` | PC/MOBILE UI 구현 계획, 버전별 로드맵 |
| 전이용 컨텍스트 | 다른 채팅방으로 넘길 요약 |
| xlsx 파일 | 셀 위치/현재 데이터 확인용. 수식 source of truth 아님 |

주의:

- Google Sheets 파일을 `.xlsx`로 변환하면 전용 함수가 깨질 수 있다.
- xlsx는 구조 확인용이고, 정확한 수식은 architecture spec을 따른다.

# 20. 최종 운영 원칙

- 사용자에게는 짧고 보기 좋은 검색 결과를 보여준다.
- 관리자에게는 넓고 정확한 DB를 유지한다.
- 검색엔진과 helper는 숨긴다.
- taxonomy는 확장 가능하지만, 사용자 드롭다운은 압축할 수 있다.
- 링크와 가사는 완벽하지 않아도 프로젝트 진행을 멈추지 않는다.
- 부른 횟수와 가사_INDEX는 장기적으로 추천/로그/방송 운영에 연결한다.
- Google Sheets MVP를 우선하고, Streamlit/Apps Script는 실제 사용성이 검증된 뒤 검토한다.
